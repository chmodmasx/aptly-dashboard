# Application updates

## Principle

Aptly Dashboard updates itself from **signed GitHub Releases**.

It does not run `git pull`, fetch source code, or compile itself on the user's machine.

The implementation should use Tauri v2's updater plugin.

## User experience

Settings → Application should show:

- current application version;
- update channel;
- last update check;
- **Check for updates** button;
- automatic update-check toggle;
- update notes when a newer release exists;
- download progress;
- **Install and restart** action.

Example:

```text
Application
────────────────────────────────────
Version              0.4.1
Channel               Stable
Automatic checks      On
Last checked          2 minutes ago

[ Check for updates ]

Update available: 0.5.0
Repository profiles, task viewer improvements...

[ Download and install ]
```

## Release source

The stable updater endpoint should use a static updater manifest published with the latest GitHub Release, for example:

```text
https://github.com/chmodmasx/aptly-dashboard/releases/latest/download/latest.json
```

Tauri release artifacts and `latest.json` are generated by CI.

## Integrity

Updater artifacts must be signed.

The application embeds only the Tauri updater **public key**. The corresponding private signing key is stored as a GitHub Actions secret and is never committed to the repository.

The updater must verify the artifact signature before installing it.

## Channels

Initial release:

- `stable` only.

Later, if useful:

- `beta` / prerelease channel.

Do not mix prereleases into the stable updater endpoint.

## Startup behavior

Recommended default:

- make a lightweight background check once after application startup;
- never install an update without user confirmation;
- expose a setting to disable automatic checks;
- always keep the manual **Check for updates** button.

If GitHub is unreachable, the application remains fully usable and shows a non-blocking status.

## Development builds

The updater should be disabled or clearly marked unavailable in development builds.

## Platform rollout

Start with the platforms for which our release workflow produces and tests signed updater artifacts. Linux is the first priority.

The Settings UI should never claim update support on a package/target that CI does not actually publish.
